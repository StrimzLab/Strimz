# Refund over-payment and double-payment fixes

Closes #121.

## What was wrong

- A refund that had been created but not yet signed did not count toward the amount
  already refunded, so a merchant could create refunds that together exceeded the
  original payment.
- The API created the refund row before resolving the token address. When the address
  was not configured, the row existed but the request failed, leaving an orphan refund
  and a `refund.created` webhook.
- In the dashboard, if the on-chain transfer went out but reporting its hash to the API
  failed, clicking "Sign & submit" again sent a second transfer. The dashboard also
  built the token address from its own environment variables.

## What shipped

- The cap now counts refunds in `pending`, `awaiting_signature`, `submitted` and
  `completed`.
- The API resolves the token address before writing anything. An unconfigured currency
  returns 400 and creates nothing.
- The dashboard remembers the transaction hash in browser storage as soon as the
  wallet returns it. A retry submits that hash instead of signing again, and the entry
  is cleared once the API accepts it. If browser storage is unavailable, the dashboard
  warns the merchant not to sign twice.
- The dashboard takes the token address for a currency from `@strimz/shared-config`
  for the configured Arc environment, the same source the checkout uses.

## Not changed

The API still returns signing instructions only on create. A merchant who returns to a
refund later gets the instructions rebuilt in the dashboard. Serving them from the API
for an existing refund would add an endpoint to the SDK, which needs an ADR.
