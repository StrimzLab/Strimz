---

Hosted is the path most merchants take. Embedded is the answer when a redirect doesn't fit, usually because the checkout is one step inside a multi-step product flow that you don't want to break.

With embedded, the checkout renders inside your page instead of on a separate one. Strimz still owns the wallet flow, the relayer, and the on-chain submission. You own the page around it.

## When to actually pick embedded

A few cases where it makes sense:

You have a multi-step checkout and payment is one step in the middle. A redirect would drop the customer out of your flow and back in again.

You have a specific UI requirement. Inline forms, side-panel checkouts, modal-based flows. That doesn't map onto a redirect. (Most "I want a different layout" cases actually want hosted with a slightly different framing; embedded is for when the layout genuinely can't redirect.)

The embedded checkout is the hosted checkout in a frame, so the payer still sees the Strimz checkout UI and connects their wallet inside it.

If none of those apply, stay on hosted. You'll ship faster and have less to maintain.

The two packages: `@strimz/sdk` gives your server `StrimzClient`, which takes your secret key and must never run in the browser. `@strimz/sdk-react` is the browser layer: a provider, hooks, and components that use a publishable key. It has no TanStack Query dependency.

## Server-side: create the session

Same as hosted. The session doesn't care where the payer is going to sign.

```ts title="app/api/checkout/route.ts"
import { StrimzClient } from '@strimz/sdk'

const strimz = new StrimzClient({ apiKey: process.env.STRIMZ_API_KEY! })

export async function POST() {
  const session = await strimz.paymentSessions.create({
    amount: '10000000',
    currency: 'USDC',
    description: 'Pro plan, monthly',
  })

  // Return the session id, not the checkoutUrl, we're handling the UI ourselves.
  return Response.json({ sessionId: session.id })
}
```

## Client-side: mount the provider

`StrimzProvider` carries the publishable key. It is the only key the browser ever sees.

```tsx title="app/providers.tsx"
'use client'

import { StrimzProvider } from '@strimz/sdk-react'

export function Providers({ children }: { children: React.ReactNode }) {
  return (
    <StrimzProvider publishableKey={process.env.NEXT_PUBLIC_STRIMZ_PUBLISHABLE_KEY!}>
      {children}
    </StrimzProvider>
  )
}
```

Render `<Providers>` around your app in your root layout. The publishable key is browser-safe. See [API keys](/docs/dashboard/api-keys) for what it can and can't authorize.

## Client-side: embed the checkout

`StrimzCheckoutEmbed` renders the Strimz checkout for a session inline, in an iframe on your page. The payer connects a wallet and signs inside the frame, so you don't wire a wallet stack yourself.

```tsx title="components/checkout-panel.tsx"
'use client'

import { StrimzCheckoutEmbed, useStrimzSession } from '@strimz/sdk-react'

export function CheckoutPanel({ sessionId }: { sessionId: string }) {
  const { session, error } = useStrimzSession(sessionId)

  if (session?.status === 'confirmed') return <p>Paid. Thank you.</p>
  if (error) return <p>Could not load the payment: {error.message}</p>

  return <StrimzCheckoutEmbed sessionId={sessionId} height={640} />
}
```

`useStrimzSession` reads the session with the publishable key and polls until it reaches a terminal state (`confirmed`, `failed`, `expired`, or `cancelled`), so the panel switches to its success state on its own.

If you'd rather open the checkout in a popup from your own button, use `<StrimzPayButton sessionId={sessionId} />` or the `useStrimzCheckout()` hook, which returns `{ open(sessionId), close(), status }`.

## What you still own

The surrounding UI. Where the checkout sits, what the page says around it, and what you show before and after payment.

The success UI. `useStrimzSession` gives you the session and its status; what you do with it is up to you. Most merchants show a confirmation screen and link to their next step.

Fulfilment. Grant access or ship the order from your [webhook handler](/docs/guides/webhooks), not from the browser. The browser can be closed or tampered with; the signed webhook can't.

## What Strimz still owns

The wallet flow. Wallet connect, the typed-data prompts, and the chain switch all happen inside the checkout.

The relayer. We pay the gas. We broadcast.

The indexer. We watch for the on-chain confirmation and project it into the session.

The webhook. Once the indexer confirms, we fire `payment.completed` to whatever endpoints you've subscribed.

The state machine. The session statuses are driven entirely by Strimz's backend; the React SDK reads them but doesn't write them.

## Subscriptions, briefly

The React SDK opens payment sessions only. For recurring billing, send the payer to the hosted plan link (`/sub/<planId>`). See [Plans](/docs/subscriptions/plans).

See [`@strimz/sdk-react`](/docs/sdks/react) for the full component and hook surface.
