title: Glossary
description: Strimz-specific terms and what they mean.
---

A handful of terms in these docs are worth pinning down up front. Some
come from card-payments vocabulary. The rest are specific to billing
on a stablecoin chain.

## API key kinds

**Secret key.** Full permissions, server-side only. Prefixed `sk_test_` in test mode and `sk_live_` in live mode.

**Publishable key.** Identifies browser calls and grants no access. The public checkout and token routes do not check it, and every other route rejects it. It cannot create a payment session. Safe to ship in a browser. Prefixed `pk_test_` in test mode and `pk_live_` in live mode.

## Charge attempt ID

A 32-byte deterministic identifier passed to the contract's `batchCharge` so retries are safe. Computed as `keccak256(abi.encodePacked(onchainSubId, currentPeriodEndAt, attempt))`, with `attempt` from 0 to 7. The contract's `usedAttempts` mapping skips a reused id with outcome `Duplicate` instead of charging again.

## EIP-2612

The "permit" standard. The payer signs a structured message that
grants a contract an ERC-20 allowance. USDC and EURC both implement
it natively. Strimz uses it in the subscription enrolment call
(`permitAndCreateSubscription`), alongside a second signed
`SubscriptionIntent`. The
[meta-tx flow page](/docs/concepts/meta-tx-flow) walks through the
full sequence.

## EIP-3009

The "transfer with authorization" standard. The payer signs a
structured message authorising a specific recipient to pull a specific
amount of a specific token. USDC and EURC implement it natively.
Strimz uses it for the single-signature one-shot payment call
(`payWithAuthorization`). See the
[meta-tx flow page](/docs/concepts/meta-tx-flow) for the wire-level
detail.

## EIP-712 typed-data

The format a wallet uses to display a structured message instead of a
raw transaction or an opaque `personal_sign` blob. EIP-3009 and
EIP-2612 are both built on top of it, which is how the wallet renders
human-readable fields like `from`, `to`, `value`, and `deadline`
rather than a hex string.

## ERC-7201

The "namespaced storage" pattern. It lets a contract park its state
at a deterministic slot so adding fields later can't collide with the
previous layout. Strimz's upgradeable contracts use it.

## Idempotency key

A string the client picks per write, so the API can dedupe retries.
The SDK sends one in the `X-Strimz-Idempotency-Key` header on every
`POST` and `PATCH`. The API replays the first response for the same key
for 24 hours. See [Idempotency](/docs/concepts/idempotency).

## Live mode

Real payments on Arc mainnet, with `sk_live_` and `pk_live_` keys. Its counterpart is
[test mode](#test-mode). See [Test mode and live mode](/docs/testing).

## Meta-tx

Short for "meta-transaction." The customer signs a structured message
off-chain. A third party (Strimz) wraps that signature into
a transaction and broadcasts it. The customer pays no gas. Strimz
pays the network fee but cannot move funds on its own; the contract
verifies the customer's signature on every call. `payWithAuthorization`
and `permitAndCreateSubscription` are both meta-tx entrypoints.

## Mode

A field on most resources (`subscription.mode`, `transaction.mode`, etc.) recording whether it was created in test or live mode.

## On-chain merchant ID

A `uint96` assigned by `StrimzRegistry` when a merchant first registers their payout wallet on-chain. Exposed on session/plan payloads as `chainMerchantId`. The contracts use it (not the off-chain `cuid`) as the canonical merchant identifier.

## Permit nonce

A per-owner monotonic counter that EIP-2612 tokens maintain. The
current value goes into the signed permit; every successful permit
increments it on-chain. A stale nonce reverts. Read it just before
signing via `tokens.permitNonce(token, owner)`.

## Pull-based subscription

The customer signs once, granting the contract a multi-period
allowance. Strimz then "pulls" payment each period.
The opposite is push-based, where the customer initiates each charge
themselves.

## Ref

A `bytes32` identifier passed to `StrimzPayments.pay()` and
`payWithAuthorization()`. Strimz uses it to match an on-chain
payment to its payment session.

## Network fee

The gas a transaction costs on chain. Strimz broadcasts payer-signed
authorisations and pays the network fee, so the payer needs no gas.
The contracts authorise the payer's signature, not Strimz's key, so
Strimz's key cannot be used to move customer funds.

## Sub-tenancy

The `parentMerchantId` field on `StrimzRegistry`. Lets a merchant
register under another merchant for hierarchical billing arrangements:
resellers, agency-of-record relationships, multi-brand orgs. Charges
still settle to the child merchant's own `payoutAddress`. The parent
field is metadata the reseller can reconcile against.

## UUPS

Universal Upgradeable Proxy Standard (EIP-1822). Used by Strimz's
policy contracts: Registry, FeeCollector, TokenWhitelist, and AgentRegistry
and AgentEscrow once agent escrow ships. `StrimzPayments` and `StrimzSubscriptions`
are not UUPS. They are deliberately immutable.
[On-chain architecture](/docs/concepts/on-chain-architecture) covers
why the line falls where it does.

## Test mode

Strimz on Arc testnet, with `sk_test_` and `pk_test_` keys and free test USDC from Circle's
faucet. Every account has a test side and a live side, and they never share data. See
[Test mode and live mode](/docs/testing).

## Webhook delivery

One event sent to one endpoint, with up to 5 attempts. Strimz keeps
each delivery, so you can see the latest attempt's response code and
body in your dashboard.

## Webhook signing secret

The HMAC key Strimz uses to sign outbound webhook deliveries.
Generated when you create the endpoint and returned to you exactly
once. Strimz stores it encrypted.
