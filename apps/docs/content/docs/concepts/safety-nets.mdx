---
title: Safety nets
description: The checks that stop a payer paying twice, a subscription enrolling twice, a bad redirect URL, or a paid subscriber being marked at risk. Each one stays out of the happy path.
---

Safety nets aren't optimizations. They're the layers you build because you've seen the thing they prevent. Every mechanism on this page exists because of a real edge case.

The general principle: critical guarantees should be enforced by _more than one_ layer. If your double-pay protection is one check, a single bug in that check wipes you out. If it is three independent layers, a bug in one of them is recoverable.

## Three layers against double-pay

A payer hits "Pay," the page is slow to react, they click again. Without protection, two on-chain submissions go out and two settlements happen. Strimz prevents this three ways, each independent.

The first layer is the settlement record. Once `PaymentSettled` lands on chain and Strimz sees it, the session's `onchainTxHash` is set. Before sending a new transaction, Strimz checks it. If there's already a tx hash, it returns the existing confirmation instead, and nothing new goes on chain.

The second layer is a second check just before sending. Strimz looks for the same session already in `submitted` or `confirmed` state with a tx hash. If it finds one, it returns the existing confirmation. This catches the short window where the payment has confirmed but the first check hasn't caught up yet.

The third layer is on the hosted checkout page itself. The page polls `GET /v1/payment-sessions/:id` every two seconds while the user is on the page. The moment status flips to `confirmed`, the Sign button is replaced with a "Paid" state. Clicking does nothing.

In normal operation only the third layer matters. Most users would never click twice fast enough to escape the polling interval. But the first two layers are there for the edge cases: bots, network re-tries from the user's wallet software, a connection that keeps dropping the request mid-flight. Any single layer would catch the duplicate in normal cases. All three together make double-pay structurally impossible.

## Double-enrolment protection for subscriptions

Same problem, different resource. A payer signs the EIP-2612 permit, the page is slow, they sign again. Two subscriptions for the same plan.

The first layer is the enrolment transaction. Strimz records the transaction that created each subscription, and two subscriptions can never share one. A second attempt comes back as a clean "already enrolled" error.

The second layer is a check before sending `permitAndCreateSubscription(...)`. If the same wallet already has an active subscription to the same plan, Strimz returns the existing subscription. The payer's wallet pops a second prompt, they sign it, but the second signature is never submitted on chain.

You see one subscription. The payer sees one charge. The contract sees one `SubscriptionCreated` event.

## Callback URL allowlist

This one came from an audit reviewer. The original `successUrl` and `cancelUrl` fields were validated as URLs but didn't restrict the protocol. The reviewer pointed out that a malicious merchant could set `successUrl: 'javascript:alert(1)'` , and when the payer's wallet redirected to that URL, the JavaScript would run in the wallet's WebView context. Not catastrophic in most wallets but absolutely not okay.

The fix is a strict allowlist:

```ts
const callbackUrlSchema = z
  .string()
  .url()
  .refine((v) => v.startsWith('https://') || v.startsWith('http://'), {
    message: 'must be an http:// or https:// URL',
  })
```

A `successUrl` or `cancelUrl` that isn't `http://` or `https://` is rejected at `paymentSessions.create`. It is never stored and never used for a redirect.

We allow `http://` because some merchants use it in local dev. Production should always be `https://`; the warning shows up in the dashboard if you create a live-mode session with an `http://` callback.

## The race-condition guard

Strimz checks for due subscriptions every 15 minutes, and it can take a few seconds to see a successful charge on chain. If a check runs in that window, Strimz may try to charge a period that is already paid. The contract skips it with `NotDue` or `Duplicate`.

Treating that skip as a failure would downgrade a payer who did pay to `at_risk`.

So skip outcomes are split in two. Only payment failures (`InsufficientFunds`, `RevokedApproval`, `MerchantInactive`, `TransferFailed`) move an `active` or `at_risk` subscription to `at_risk`, fire `subscription.charge_failed` and schedule a retry. A `NotDue`, `Duplicate`, `Ended` or `Unknown` skip is still recorded for the audit trail, but the subscription's status and retry timer are left alone. A successful charge always resets the subscription to `active` and clears the retry state.

## What they have in common

All four are silent during normal operation. None of them slow down a successful payment or a successful charge. They only do work when something unusual happens: a double-click, a malicious URL, a network race. The cost of running them is essentially nothing.

The cost of _not_ running them is one bad week per incident. We'd rather have the small ongoing cost than the rare big one.
