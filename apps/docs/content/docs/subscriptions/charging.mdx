---
title: How charges fire
description: Strimz checks for due subscriptions every 15 minutes and charges each one on chain. The contract refuses a double charge, and every attempt ends in a recorded outcome.
---

Strimz checks for due subscriptions every 15 minutes and charges them. A subscription is charged within about 15 minutes of its due date. Each subscription is charged on its own, so one failing subscription cannot hold up the others.

Before charging, Strimz checks that the subscription is not `cancelled` or `lapsed` and asks the contract whether the charge is due. If it is not due, nothing happens until the next check.

## The on-chain call

```solidity
function batchCharge(
  uint256[] calldata subscriptionIds,
  bytes32[] calldata chargeAttemptIds
) external returns (ChargeOutcome[] memory outcomes);
```

Strimz sends the transaction and pays the network fee. The payer's signature from when they subscribed is what authorises the charge, and the contract only moves the plan's amount once per period.

Every charge carries a charge attempt id:

```
keccak256(abi.encodePacked(uint256 onchainSubId, uint64 currentPeriodEndAt, uint32 attempt))
```

`attempt` runs from 0 to 7, so a period gets at most 8 attempts. The id is deterministic, so replaying the same attempt gives the same id. The contract records used ids. A second call with a used id does not revert: the contract emits `SubscriptionChargeSkipped` with outcome `Duplicate` and moves on. The contract marks an id used only when it attempts the transfer, so on `Charged` or `TransferFailed`. Skips before that point, such as `InsufficientFunds`, leave the id unused, and the next retry sends the same id again. After a `TransferFailed`, the next retry uses the next attempt number.

No failure reverts the call. Each subscription gets an outcome:

| Outcome             | Meaning                                    |
| ------------------- | ------------------------------------------ |
| `Charged`           | The payer was charged                      |
| `Duplicate`         | This attempt id was already used           |
| `Unknown`           | No subscription with this id               |
| `Cancelled`         | The subscription is cancelled              |
| `NotDue`            | `nextChargeAt` is still in the future      |
| `Ended`             | The subscription is past its end time      |
| `RevokedApproval`   | The allowance is too low                   |
| `InsufficientFunds` | The balance is too low                     |
| `MerchantInactive`  | The merchant is not active in the registry |
| `TransferFailed`    | The token transfer failed                  |

If a subscription is more than one period behind, the contract charges one period and moves `nextChargeAt` past the missed ones. It does not charge for each missed period.

## What you see

There is no separate API route for listing charges. They arrive in the `subscription.charged` and `subscription.charge_failed` webhook payloads.

When Strimz sees `SubscriptionCharged` on chain, it records a succeeded charge and the transaction, moves the period forward, resets the retry counter, sets `trialing` or `at_risk` subscriptions to `active`, and fires `subscription.charged`.

When Strimz sees `SubscriptionChargeSkipped`, it records a failed charge with the outcome. Only payment failures (`insufficient_funds`, `revoked_approval`, `merchant_inactive`, `transfer_failed`) fire `subscription.charge_failed` and move an `active` or `at_risk` subscription to `at_risk`. The [race-condition guard](/docs/concepts/safety-nets#the-race-condition-guard) keeps a subscription that already paid this period from being downgraded. Other outcomes such as `not_due` and `duplicate` are recorded and nothing else happens. In the API, `skipped` is the fallback for an outcome the contract adds later.

## When charges don't fire

- `nextChargeAt` is in the future. This is the normal case.
- The subscription failed recently and is waiting for its next retry. See [Recovery](/docs/subscriptions/recovery).
- The subscription is `cancelled` or `lapsed`.
- The subscription has not been confirmed on chain yet.

A subscription in `trialing` is charged when its trial ends. Archiving a plan does not stop charges for existing subscribers.

There is no call to trigger a charge on demand. The next check picks up anything due.
